# 18. 개인별 종목 카드 — 비용이 구독자 수를 따라가지 않는 구조

상태: **v0.1 제안(2026-10-10).** Nick 질문(15:15): "유료 상품에서 개인별로 다른 종목 정보를 제공하는 시스템은 어떤 식으로 비용 효율적으로 구축할 수 있겠어?" 정해진 것은 없다. 정하면 `plan/decisions.md`에 적는다.
전제: 개인별로 **보내는** 것은 1332 5번 답 전에는 열지 않고 약속하지도 않는다(D37). 이 문서는 답이 어느 쪽이어도 버리는 것이 없는 구조를 적는다.

## 1. 한 줄

**카드는 종목마다 한 번만 만들고, 사람마다 다른 것은 "어떤 카드를 받는가"뿐이다.** 그러면 비용은 구독자 수가 아니라 다루는 종목 수와 카드의 깊이를 따라간다. (D21 "개인별 레터는 표준 카드의 조립"을 시스템으로 옮긴 것)

## 2. 세 층

| 층 | 하는 일 | 무엇에 비례하나 |
|---|---|---|
| ① 카드 만들기 | 종목마다 주 1회 카드 한 장을 만들어 DB에 둔다(칸별 값 + 그려 둔 HTML). 실적이 나온 날만 한 번 더 | 다루는 종목 수 |
| ② 고른 종목 | 구독자가 고른 종목 목록. 보유 수량 · 매수가는 받지 않는다 | 구독자 수(값은 몇 글자) |
| ③ 조립과 전달 | 보낼 때 구독자의 목록대로 ①의 카드를 이어 붙인다. 새로 쓰는 문장은 없다 | 구독자 수(메일 한 통, 호출 한 번) |

돈과 손이 드는 곳은 ①뿐이다. 그래서 줄일 곳도 ①이다.

## 3. 비용을 줄이는 다섯 가지

1. **카드를 두 등급으로 나눈다.**
   - **손이 가는 카드**(다섯 종목 + 신청이 가장 많은 한두 종목): 소식 + 도움 / 부담 / 반반 + 풀이. LLM이 초안을 쓰고 Nick이 본다(`templates/news_labels.md` 7번)
   - **코드 카드**(그 밖의 모든 종목): 이번 주 일정, 최근 공시의 제목과 날짜(표시 없음), 지난 분기 실적, 현재 상태, 과거 기록과 비교. 사람 손 0, 판단 문장 0
   - 유료의 값은 "사람이 쓴 분석을 더 많은 종목에"가 아니라 "같은 틀을 내 종목에 + 코드가 계산한 깊이"다. 사람이 쓰는 칸을 종목 수만큼 늘리면 평일 90분이 먼저 바닥난다
2. **고를 수 있는 종목을 목록으로 둔다.** 처음에는 예탁결제원 보관금액 상위 50종목. 신청이 쌓이는 종목부터 넓힌다. 그리고 **한 명이라도 고른 종목의 카드만 만든다**
3. **자료는 무료인 것부터.** 회사 공시와 실적 숫자는 미국 증권거래위원회 공시(EDGAR)에서. 가격으로 계산하는 "상태"는 벤더 계약이 필요하고(D26, 견적 대기) 이것은 개인화와 관계없이 드는 고정비다
4. **보내는 것은 지금 쓰는 도구로.** 스티비 자동 이메일 API는 구독자마다 다른 값을 본문의 `$%key%$` 자리에 넣어 보낸다(스탠다드 이상, 1초 3회, 1회 256KB — https://help.stibee.com/email/automation/api). 구독자 1,000명이면 6분쯤. 값에 HTML을 넣는 것은 "호환성을 보장하지 않는다"고 적혀 있어 시험이 필요하다. 안 되면 Amazon SES(1,000통에 $0.10 — https://aws.amazon.com/ses/pricing/)로 직접 보내되 수신거부 · 반송 처리를 우리가 맡게 된다
5. **LLM은 손이 가는 카드에만, 주 1회 묶어서.** 돌리기 전에 요금의 상한을 먼저 잰다(엔진 실행기의 estimate와 같은 방식, D34)

## 4. 규제 답에 따라 갈리는 것은 전달뿐이다

| | 조회형 (답 전, 또는 "안 된다") | 발송형 ("된다") |
|---|---|---|
| 무엇 | 모두에게 같은 메일 + 유료 구독자는 웹에서 종목을 골라 직접 본다 | 화요일 메일에 "내 종목" 칸이 붙는다 |
| 만드는 것 | 카드를 그려 둔 정적 페이지(S3 + CloudFront), 유료 구독자의 메일에 든 전용 링크. 고른 종목은 브라우저에 저장 | 스티비 API 호출(또는 SES) |
| 서버 | 로그인 · 계정 시스템 없이 시작한다 | 예약 작업 하나("내 종목 발송") |

①과 ②는 두 경우에 같다. 그래서 ①부터 만든다 — 무료 메일의 다섯 종목 카드 자동화(11월 예정)가 곧 ①의 첫 판이다.

## 5. 만드는 차례 (제안)

| 때 | 만드는 것 | 비고 |
|---|---|---|
| 11월 | 카드 DB + 다섯 종목 카드 자동화. 종목을 가리지 않는 틀로 | 이미 예정된 "종목 카드 v0" |
| 11월 하순 | 코드 카드를 상위 50종목으로 돌려 빈칸이 얼마나 나오는지 본다 | ETF · 미국 밖 회사(ADR)는 공시 형식이 달라 빈칸이 생길 수 있다 |
| 유료 시작 | 웹 조회판 + 전용 링크 | 규제 답과 관계없이 선다 |
| 5번 답 뒤 | 메일의 "내 종목" 칸(스티비 API 시험 → 발송) | |

## 6. 정할 것 (세션의 추천)

1. 고를 수 있는 종목: **상위 50종목부터**(추천) / 처음부터 전 종목
2. 그 밖 종목의 카드: **코드 카드로**(추천) / 소식 풀이까지 LLM으로 자동(검수 없이 나가므로 권하지 않는다)
3. 먼저 만들 전달: **웹 조회**(추천 — 5번 답을 기다리지 않는다) / 메일 발송

## 7. 확인하지 못한 것

- 스티비 API의 값에 카드 HTML을 넣었을 때 메일 앱에서 그대로 보이는지
- 실적 발표일을 50종목에 대해 자동으로 받을 무료 출처(다섯 종목은 회사 공지를 손으로 본다)
- 가격 자료의 계약 조건과 값(D26)
- 전용 링크가 다른 사람에게 전달되는 것을 어디까지 막을지(처음에는 막지 않고 본다)
- 결제 수단(미결)에 따라 "누가 유료인가"를 어디서 읽는지 — 스티비 유료 구독이면 스티비 주소록, 자체 결제면 우리 DB
