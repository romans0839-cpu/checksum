## 0. 한 문장

**같은 자료를 두 엔진에 주고, 미국 경제지표의 발표값을 발표 전에 봉인하고, 발표 뒤 같은 자로 채점한다.**
해자는 "잘 맞힌다"가 아니라 "한 번도 빼지 않고 봉인하고 채점한 기록의 길이"다.

## 1. 왜 하는가, 무엇을 기대하는가

- **전망 체크의 짝.** 남의 전망을 채점하는 곳이 자기 전망도 같은 자로 채점한다. 장부·채점표(D12)와 같은 원리를 하나 더 쌓는 일이다.
- **일정 체크의 재미.** "수요일 밤 물가 발표"에 "두 엔진은 얼마로 봤나"가 붙는다. 구색이 풍부해진다(D14).
- **정확도는 가설로 등록하고 기록으로 가린다.**
  - Nick의 가설(10/5 등록): "최신 모델로 만든 엔진은 시장 예상치만큼 맞힌다. 아직 아니라면 곧 그렇게 된다." 사람들의 그 기대감 자체가 소구점이다.
  - 지금까지의 근거: 지표 예측을 실시간으로 잰 연구(arXiv 2608.30110)에서는 LLM이 시장 예상치와 비슷하거나 조금 못했고 물가에서 뒤졌다. 다만 평가된 것은 한 세대 전 모델이다. 일반 예측 질문에서는 최상위 LLM과 슈퍼예측가의 격차가 "LLM 발전 1년치"까지 좁혀졌고, 추세선상의 동률 시점은 2026년 11월 전후(95% 구간 2026-01 ~ 2027-11)로 추정됐다(ForecastBench, 2026-01). 최신 모델(Astra, Fable 세대)로 지표 예측을 잰 공개 결과는 찾지 못했다. → 가설이 맞는지 틀리는지 아직 아무도 재지 않았고, 우리 장부가 재는 쪽이 된다.
  - 모델과 무관하게 남는 불리함: 엔진은 시장 예상치를 입력으로 받지 못하고(유료 자료) 발표 12시간 전에 마감한다. 그래서 승부처는 입력 자료다(docs/13).
  - 가리는 방법: 핵심 발표마다 시장 예상치를 발표 전에 내부 기록으로 남기고(§6) 같은 자로 채점한다. 판정 시점은 발표 30회.
  - 기대감을 쓰는 방식: "두 AI 엔진이 맞히는지 같이 지켜본다"는 쓸 수 있다. "AI가 기관보다 정확하다"는 기록이 생기기 전에는 쓰지 않는다(단정적 판단 금지, D12).
- **정확도를 올릴 수 있는 곳은 레시피다.** 어떤 자료를 어떤 순서로 주는지, 지표를 어떻게 쪼개 묻는지, 몇 번 돌려 어떻게 합치는지. 이 부분이 비공개 로직이 된다. 내용은 감추되, 바뀌지 않았다는 것은 해시로 증명한다(§4).
- **정확도를 카피로 쓰지 않는다.** "적중률 N%"는 수익률 자랑과 같은 함정이다(D12). 틀린 것도 같은 크기로 싣는다.

## 2. 지킬 선 (D18)

1. 대상은 **연방 통계기관이 정해진 날 숫자로 발표하는 지표**뿐이다. 주가·지수·환율·개별 종목 실적·기준금리 결정은 예측하지 않는다.
2. **과거 데이터로 성능을 재지 않는다.** 모델은 과거 값을 이미 알고 있어 백테스트가 부풀려진다. 성적은 봉인 이후의 기록만 센다.
3. **엔진 = 이름 + 버전 + 기반 모델 + 레시피.** 무엇이든 바꾸려면 새 버전을 장부에 먼저 등록한다. 성적은 버전별로 따로 센다.
4. 엔진 **이름에 모델 회사·모델 이름을 넣지 않는다.**
5. 예측 문장 옆에 **가격 방향·행동 권유 문장을 두지 않는다.**
6. 엔진이 낸 값은 **사람이 고치지 않는다.** 검수는 형식과 표기만 본다.
7. **예측은 한 번만 낸다.** 같은 발표에 다시 내지 않는다.

## 2-2. 전망판과 해석 (D21)

- **전망판**: 분기 1회(FOMC 경제전망이 나오는 3·6·9·12월). 3·6·12개월 앞의 물가·실업률·성장률을 범위로 내고 연준 전망과 나란히 놓는다. 다음 발표값 예측과 같은 규칙으로 봉인하고, 해당 달의 발표값으로 채점한다. 기준금리 결정·주가·지수·환율·개별 실적은 계속 대상이 아니다. 1호 후보는 12/9 FOMC 뒤. 대상 지표와 봉인 형식은 12월 전에 정해 코드에 넣는다.
- **해석**: 숫자와 함께 엔진의 해석을 싣는다. 네 칸 — 가운데 길 / 위로 벗어나는 경우 / 아래로 벗어나는 경우 / 무엇을 보면 알 수 있나.
  1. "아들러의 해석", "플레처의 해석"으로 표시를 단다.
  2. 한쪽으로 단정하지 않는다. 양쪽 경우를 함께 쓴다.
  3. 봉인된 범위에 묶는다(위쪽 경우 = 범위의 위 끝 쪽). 다음 호에서 어느 경우였는지 되짚는다. 되짚을 수 없는 말은 쓰지 않는다.
  4. 지표와 경기에 대해서만 쓴다. 가격·종목·행동으로 잇지 않는다. 원인 단정을 쓰지 않는다.
  5. 숫자는 사실 묶음과 봉인된 범위에 있는 것만 쓴다(D17). 해석 문장은 엔진이 쓴 그대로 싣고, 규칙을 어긴 문장은 고치지 않고 뺀다.
- **종목에는 엔진을 쓰지 않는다.** 엔진은 봉인·채점되는 것만 말한다.

## 4. 엔진의 정의와 이름

**엔진 = 이름 + 버전 + 기반 모델 + 레시피 폴더 + 실행 횟수.** 레시피 폴더(`data/private/engines/<이름>/v<버전>/`)에는 프롬프트와 설정이 들어가며 밖에 내지 않는다. 등록하면 폴더 전체의 해시가 공개 장부에 남는다. 등록 뒤 파일을 하나라도 고치면 봉인 단계에서 걸린다.

레시피를 고치는 규칙: 새 버전은 먼저 '도전자'로 등록해 같은 발표를 함께 봉인하고(공개 성적에는 넣지 않음), 분기 심판 때 현 버전과 나란히 놓고 교체 여부를 정한다. 한두 번의 결과를 보고 고치지 않는다.

### 이름 — 아들러 / 플레처로 확정 (D19)

- **아들러**(`adler`) = Claude 계열 모델, **플레처**(`fletcher`) = GPT-6 Astra(`gpt-6-astra`). 짝은 엔진을 등록하기 전까지 바꿀 수 있다.
- 아래는 검토했던 후보.

| 안 | 이름 | 뜻 | 장점 | 걸리는 점 |
|---|---|---|---|---|
| **A (추천)** | **아들러 / 플레처** | 체크섬을 계산하는 실제 방법의 이름(Adler-32, Fletcher) | 브랜드와 한 줄로 이어진다. 사람 이름처럼 불려 "이번에는 아들러가 더 가까웠다"가 자연스럽다. 정확도를 약속하지 않는 이름 | 유래를 한 번은 설명해야 한다(운영자 노트 소재) |
| B | 가늠 / 어림 | 순우리말 | 쉽고 겸손하다. '예측'보다 '가늠'이라는 태도가 드러난다 | 둘의 구분이 약하다. '어림'은 허술하게 들릴 수 있다 |
| C | 눈금 / 저울 | 재는 도구 | '체크'와 어울린다 | 캐릭터가 약하고 도구 메뉴 이름과 헷갈릴 수 있다 |

- 코드에서 쓰는 이름은 영문 소문자(`adler`, `fletcher`), 화면 이름은 한글.
- 어느 엔진이 어느 모델 위에서 도는지는 **이름에는 넣지 않되, 방법 페이지의 버전 표에는 사실로 적는다.** 감추면 "과정을 공개한다"는 포지션과 어긋난다.
- 공개 전에 할 일: 상표 검색(KIPRIS), 모델 제공사의 표기 지침 확인.

## 5. 입력 — 두 엔진이 같은 사실 묶음을 본다

- 대상 지표의 과거 값(최근 36개월)과 구성 항목, 직전 발표의 수정 이력
- 발표 전에 먼저 나오는 공공 자료: 주간 휘발유 소매가(에너지정보청), 주간 실업수당 청구(노동부), 같은 달의 다른 발표(예: CPI 예측에 고용보고서)
- 달력 정보: 조사 주간, 영업일 수, 작년 같은 달의 전월비(기저 효과)
- **넣지 않는 것**: 시장 예상치(권리 없음), 기사·헤드라인(D17 원칙 — 엔진도 사실 표만 본다), 웹 검색(끈다. 켜면 남의 예상치를 옮겨 적는 복사기가 된다)
- 묶음은 파일로 저장하고 해시를 봉인 기록에 넣는다. 두 엔진에 같은 파일이 갔다는 것이 남는다.

## 6. 출력, 봉인, 채점

**출력**: 지표마다 가운데 값(p50)과 80% 구간(p10~p90). 한 점이 아니라 범위로 낸다. 발표 자릿수보다 한 자리까지만 더 잘게 쓴다.

**봉인**: 발표 한 번이 장부 기록 한 건. 마감은 **발표 12시간 전**. 공개 장부에는 발표 종류·기준 기간·엔진 목록·해시만 남고, 값은 발표 뒤에 원문으로 공개한다. 기준선("직전 발표값 그대로")도 같은 기록에 함께 봉인한다.

**코드가 막는 것**: 마감을 넘긴 봉인 / 등록되지 않은 엔진·버전 / 등록 뒤 레시피가 바뀐 엔진 / 같은 발표의 두 번째 봉인 / 기준선이 빠진 지표 / 구간 순서가 틀린 값.

**채점** (발표 다음 날):

| 보는 것 | 뜻 |
|---|---|
| 오차 | 가운데 값과 발표값의 차이 |
| 구간 적중 | 발표값이 p10~p90 안에 들어왔는가. 길게 보면 80%여야 한다. 그보다 높으면 구간이 너무 넓고, 낮으면 과신이다 |
| 구간 점수 | 구간 폭 + 벗어난 거리 × 10. 좁으면서 맞을수록 작다 |
| 기준선과 비교 | 같은 발표·같은 지표에서 "직전 값 그대로"보다 오차가 작았는가 |

- 단위가 다른 지표의 오차를 한 숫자로 합치지 않는다. 지표별로 따로 보여 준다.
- 발표 30회 미만은 "표본 부족"으로 표시한다. 한 발표 안의 값들(예: CPI 3개)은 서로 묶여 있어 발표 횟수로 센다.
- 시장 예상치·지역 연은 예측과의 비교는 권리 문제로 **내부에서만** 한다(§9). 공개 비교 대상은 당분간 "직전 값 그대로" 하나다. 쉬운 기준선이므로 이긴 것을 내세우지 않는다.
- **시장 예상치 내부 기록**: 핵심 발표(월 3~4회)마다 발표 전날 보도된 시장 예상치를 출처 주소와 함께 `data/private/forecast/consensus.csv`에 적고, 예측과 같은 때 봉인한다(값은 공개하지 않는다). 가설(§1)을 가리는 데 필요하다. 발표당 2분쯤의 손이 든다. 봉인 방식은 실행기와 함께 만든다.

## 7. 실행 방식과 비용

| 안 | 방식 | 월 비용 | Nick의 손 | 평가 |

## 7-1. 엔진 실행기 (v0.4, 10/9 — `pipeline/forecast/runner.py`)

```
사실 묶음(DB) → 사실 표(글) → 엔진마다 n번 호출 → 답 읽기 → 번들의 가운데 값 → 예측 파일 → 봉인
```

레시피 폴더(`data/private/engines/<이름>/v<버전>/`)에 들어가는 것: `recipe.json`(회사·모델·몇 번 부를지·몇 번 이상 맞아야 내는지·형식이 틀린 답을 몇 번까지 다시 받을지·한 번에 기다리는 시간·요청 항목), `prompt.md`(사용자 메시지 틀), `system.md`(지시문). 형식은 `pipeline/forecast/README.md`.

실행기가 정해 둔 것 (레시피로도 바꿀 수 없다)

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| 웹 검색·도구 | 켤 수 없다. 레시피의 요청 항목은 정해 둔 것만 받는다 | §5 — 같은 자료만 본다 |
| 사실 표·답 형식·합치기 | 코드에 이름과 번호로 있다(`table/1`, `json/1`, `median`). 자체 시험이 해시로 지킨다. 고치려면 새 번호를 더하고 엔진을 새 버전으로 등록한다 | 레시피 해시가 그대로면 엔진이 받은 글도 그대로여야 한다 |
| 답 한 번 | 형식이 맞는 답을 받은 번은 다시 부르지 않는다. 다시 받는 것은 형식이 틀린 답뿐(레시피의 횟수까지). API·통신 오류는 답이 아니므로 세지 않고 다음 실행에서 다시 부른다. **다만 60초 넘게 기다리다 답 없이 끝난 호출은 따로 센다 — 엔진마다 발표 하나에 `부르는 횟수 × 다시 받는 횟수`(v1은 10번)에 닿으면 그 엔진은 더 부르지 않고 받은 답으로 마무리한다(10/9, runner/0.2)** | §2-7 — 예측은 한 번만 낸다. 고를 수 있는 답이 생기지 않게 |
| 답 읽기 | 글의 마지막 `}`로 끝나는 `{"forecasts": …}` 하나만 읽는다. 앞에 적은 초안이나 안쪽에 든 다른 숫자는 읽지 않는다 | 엔진이 고쳐 적었을 때 무엇이 답인지 미리 정해 둔다 |
| 합치기 | 자리마다(p10·p50·p90) 번들의 가운데 값. 발표 자릿수보다 한 자리 더 잘게, 십진수 사사오입 | 공개된 번별 답으로 누구나 같은 값을 얻는다 |
| 미제출 | 형식이 맞는 답이 레시피의 최소 횟수에 못 미치면 그 엔진은 그 발표를 내지 않는다. 뒤늦게 채우지 않는다 | §10 — 놓친 발표는 미제출 |
| 봉인 시점 | 답이 다 모인 엔진은 다른 엔진을 기다리지 않고 바로 봉인한다. 그래서 한 발표의 기록이 엔진마다 한 건씩일 수 있다(같은 묶음·같은 기준선) | 한 회사의 장애가 다른 엔진의 봉인을 막지 않게 |
| 마감 | 발표 13시간 전부터는 더 부르지 않고, 받은 답이 최소 횟수를 넘는 엔진은 그것으로 마무리한다. 12시간 전을 지나면 아무것도 하지 않는다. 마감을 늦추는 선택 항목이 없다(`seal`에서도 12시간보다 늦출 수 없게 막았다) | §6 |
| 묶음·엔진 목록 | 그 발표의 첫 답을 받는 순간에 굳는다. 그 뒤에 묶음 파일이 바뀌었거나 새 버전이 등록돼도 그 발표는 처음 것으로 끝낸다 | 두 엔진·모든 번이 같은 자료를 본다 |
| 찍는 것 | 건수·해시·토큰 수·상태만. 값과 답의 글은 화면·로그·조종판 어디에도 찍지 않는다(미리 보기도 형식만 알려 준다) | D20 |
| 쓰는 토큰 | 레시피에 한 번 부를 때의 출력 상한(생각하는 토큰 포함)을 반드시 적는다. 발표 한 번에 엔진 하나가 쓰는 토큰은 많아야 `부르는 횟수 × 다시 받는 횟수 × (입력 + 상한)`. `estimate`가 입력을 API로 세어(무료) 이 상한을 토큰과 요금으로 보여 준다 | D34 — 선불 충전이 모르는 사이에 떨어지지 않게 |

**레시피 v1의 숫자 (D34, 10/9)** — 아들러 `claude-fable-5-1`, 플레처 `gpt-6-astra`. 두 엔진의 지시문과 메시지 틀은 같고 모델과 요청 항목만 다르다.

| | 값 | 뜻 |
|---|---|---|
| 부르는 횟수 | 5 (3번 이상 맞아야 제출) | 번마다 답이 조금씩 다르다. 가운데 값을 쓴다 |
| 다시 받는 횟수 | 2 | 형식이 틀린 답은 한 번 더 받는다 |
| 출력 상한 | 16,000토큰 | 생각하는 토큰 포함. 깊이는 high |
| 입력 | 7천 토큰 안팎 (어림) | 보낼 글 9천 자쯤. 서버의 `estimate`가 정확히 센다 |
| 발표 한 번, 엔진 하나 | 최대 약 11.5만 토큰 · $4.4 | 출력이 상한의 절반이면 $2.4 |
| 최악 (틀린 답을 모두 다시 받음) | 약 23만 토큰 · $8.7 | |
| 한 달, 두 엔진 | 최대 $26쯤 (3.7만 원), 최악 $52 | 지금 수집기가 있는 발표 셋(CPI·고용·PPI) 기준. 환율 1,400원 |

- 요금은 100만 토큰당 입력 $10·출력 $50으로 계산했다. Claude는 10/9에 요금표로 확인했고, Astra는 공식 요금표에서 확인하지 못한 같은 값이다(§7).
- 위의 비용 표(§7)는 10/5에 "핵심+보조 월 9.2회"로 잡은 것이다. 경제분석국·노동부 수집기가 생겨 발표가 늘면 이 표의 "한 달" 줄도 그만큼 는다(발표 한 번의 상한은 그대로다).
- 실제로 나온 토큰은 `preview`가 한 번 불러 알려 준다. 그 숫자를 보고 상한과 깊이를 등록 전에 확정한다(등록하면 바꿀 수 없다). 상한에 걸려 끊긴 답은 쓰지 않으므로, 상한을 너무 낮게 잡으면 돈은 덜 들어도 미제출이 된다.

- 여러 번 돌려도 된다. 받은 답은 작업 폴더(`data/private/forecast/runs/<발표>_<기간>/`)에 하나씩 남고, 다시 돌리면 남은 것만 한다. 서버의 예약 작업 "엔진 봉인"이 발표 전날 낮부터 20분마다 불러 끝날 때까지 이어 간다(§7-2).
- 오래 기다리다 끊긴 호출에 상한을 둔 까닭: 회사 쪽에서는 답을 만들고 있었을 수 있어 요금이 나갔을 수 있다. 상한이 없으면 20분마다 다섯 번씩 마감까지 되풀이된다(검토에서 280번까지 나왔다). 상한까지 겪어도 더 드는 돈은 많아야 발표 한 번의 최대 요금만큼이다. 빨리 돌아오는 오류(충전 부족, 속도 제한, 장애)는 요금이 없으므로 예전처럼 세지 않는다.
- 미리 보기(`preview`)는 레시피를 등록하기 전에 실제 API로 한 번 불러 형식·걸린 시간·토큰 수를 본다. 답은 메모리에서 형식만 확인하고 버린다 — 저장하지 않고 봉인에 쓰지 않으므로 "한 번만 낸다"에 걸리지 않는다.
- 봉인 원문에는 실행 기록이 함께 남는다: 엔진이 실제로 받은 글의 해시, API가 알려 준 모델 이름, 맞는 답의 수, 토큰 수.
- 아직 하지 않는 것: 도전자 버전을 현 버전과 함께 돌리기(지금은 이름마다 가장 높은 버전만 고른다. 직접 지정은 된다), 일괄 처리(batch) 요금, 긴 응답을 조금씩 받는 방식(지금은 한 번에 받는다 — 한 번에 5분 안쪽으로 끝나는 설정을 전제로 한다).

## 7-2. 서버의 예약 작업 "엔진 봉인" (10/9)

`pipeline/console/jobs.py`의 작업표에 든 한 줄이다(docs/15 §5-2). 사람이 `runner run`을 손으로 돌리지 않는다.

| 정한 것 | 내용 | 까닭 |
|---|---|---|
| 맡는 발표 | 사실 묶음을 만들 수 있는 발표 — 지금은 CPI·PPI·고용 (`ENGINE_EVENTS`) | 수집기가 있는 것만 |
| 언제부터 | 발표 32시간 전(한국 시간 전날 13:30, 미국 겨울 시간에는 14:30)부터 20분마다 | 전날 밤 글(21시) 전에 봉인이 끝나 있고, 낮 글(12시)과 겹치지 않고, 문제가 생기면 마감(다음 날 09:30)까지 고칠 시간이 남는다 |
| 다른 발표를 기다림 | 묶음에 들어가는 다른 발표가 그 사이에 나오면 그 발표 30분 뒤부터 시작하고, 그 발표값이 수집될 때까지 부르지 않는다. 봉인 마감 4시간 전까지도 없으면 있는 자료로 부른다 | 첫 답을 받는 순간 묶음이 굳는다. 9월 PPI(10/15)는 하루 전의 9월 CPI를 보고 나서 부른다 |
| 한 바퀴의 시간 | 일꾼의 제한 600초 가운데 엔진 호출에 400초까지, 봉인과 외부 타임스탬프에 110초를 남긴다. 같은 바퀴의 앞 작업이 쓴 시간만큼 줄이고, 레시피의 한 번 부르는 시간(v1은 360초)보다 짧게 남으면 그 바퀴에는 부르지 않는다 | 제한에 걸려 봉인 도중에 끊기는 일이 없게 |
| 봇 집행 시간 | 화요일 23:20 전에 봉인까지 끝나도록 쓸 시간을 줄이고, 바로 앞에서는 부르지 않는다 | docs/15 §5의 조건 ② |
| 끝 | 두 엔진이 봉인되고 외부 타임스탬프를 받으면 끝. 미제출도 끝(뒤늦게 채우지 않는다). 타임스탬프만 못 받았으면 발표 때까지 다시 받는다 | |
| 조종판 | "오늘 현황"의 "엔진 봉인" 줄: `봉인됨 · 소비자물가 2026-09 · 봉인된 엔진 2/2: adler@1, fletcher@1`. 메모에는 엔진별 맞는 답 수·토큰·걸린 시간·오류. 값은 없다 | D20 |

- 결과 줄 읽는 법: `봉인됨`(엔진 2/2) / `일부만 봉인됨` / `진행 중`(20분 뒤 이어서) / `진행 중(오류 있음)`(메모의 "마지막 오류"를 본다) / `기다리는 중`(다른 발표값을 기다림) / `미룸`(그 바퀴에 시간이 모자람) / `미제출` / `멈춤`(사람이 봐야 한다 — 그 줄을 그대로 Claude에게).
- 엔진 글(전날 21시)의 조건 "두 엔진이 실제로 답을 내고 저장됐을 때만"은 이 줄이 `봉인됨 … 2/2`일 때다.
- 한 번에 엔진마다 5번을 함께 부른다. 회사의 속도 제한에 걸린 번은 다음 바퀴(20분 뒤)에 이어서 부른다 — 첫 봉인에서 실제로 몇 바퀴가 걸리는지 본다.
- 두 발표의 예정이 겹치면 바퀴마다 먼저 할 발표를 바꾼다. 4분기 일정표에는 겹치는 날이 없다.

| 2 공개 형태 결정 | 연말 M3 리뷰(12/30)에서 다시 보고, 발표 30회 채점 뒤(2027-01 하순 전후) 확정 | 성적과 무관하게 **첫 봉인부터 전부** 공개한다. 정하는 것은 형태뿐이다: 일정 체크에 상시로 넣을지, 분기 심판에만 실을지, 접을지 |

"전부 공개"를 미리 정해 두는 이유: 잘 나온 구간만 골라 보여 주는 것은 우리가 비판하는 방식이고, 광고 규제(우수 기간 선택 표시 금지)와도 같은 구조다. 접게 되더라도 "해 봤더니 이랬다"가 고정관념 체크 한 편이 된다.

## 11. 마지막 검토에서 고친 것과 남은 불확실성

고친 것
1. 처음에는 전년비 지표를 더 넣으려 했으나, 전년비는 기저 효과로 대부분 정해져 "직전 값" 기준선이 지나치게 쉬운 상대가 된다. CPI·PCE 전년비 하나씩만 남기고 전월비를 중심에 뒀다.
2. "30건"의 단위를 값이 아니라 발표 횟수로 바꿨다. 한 발표 안의 값들은 함께 움직인다.
3. 단위가 다른 지표의 오차를 하나로 합친 평균을 없앴다.
4. 엔진을 나중에 추가할 때 기준선이 다시 들어와 막히는 문제를 고쳤다(값이 같으면 허용, 다르면 거부).
5. 자체 시험이 실제 날짜에 따라 달라지지 않게 고쳤다(10/14 뒤에 돌리면 틀리게 나올 뻔했다).
6. 빈 장부에 엔진이 먼저 등록되면 기점 기록이 생기지 않는 문제를 막았다.
7. 애틀랜타 연은 약관을 확인하고 지역 연은 자료를 "공공"에서 "내부 비교용·허가 확인 전"으로 낮췄다.

v0.4(10/9) 실행기를 만들며 검토에서 고친 것 — 코드를 보지 않은 검토를 두 번 돌렸다
8. 처음에는 API 오류도 횟수로 셌다. 충전이 떨어지거나 회사 쪽 장애가 한 시간쯤 이어지면 그 엔진이 그 발표에서 영영 빠졌다 → 오류는 세지 않고 마감 전까지 다시 부른다.
9. 처음에는 두 엔진의 답이 다 모여야 봉인했다. 한쪽 키가 없으면 다 모인 쪽도 마감 직전에야(그때 실행이 걸리면) 봉인됐다 → 다 모인 엔진은 바로 봉인한다.
10. 번들의 평균을 이진 실수로 내서 0.085가 0.08로 내려가는 경우가 있었다 → 십진수로 계산한다.
11. 답 안쪽에 든 다른 숫자 묶음이나, 고쳐 적다 만 최종 답 앞의 초안을 답으로 읽을 수 있었다 → 글의 끝에 있는 것 하나만 읽는다.
12. 형식이 틀린 답의 끝부분을 숫자만 가려 미리 보기에 찍었는데, 숫자를 가려도 "직전보다 낮게" 같은 말이 읽혔다 → 답의 글은 한 글자도 찍지 않는다.
13. 같은 발표를 두 실행이 함께 돌면 받은 답이 서로 덮였다 → 작업 폴더를 잠근다. 답을 남길 수 없는 폴더면 부르지 않는다.
14. 두 엔진이 일꾼을 나눠 써서, 먼저 줄 선 엔진이 늦으면 다른 엔진이 한 번도 불리지 않았다 → 엔진마다 일꾼을 따로 둔다.
15. 키 오류의 설명에 키의 끝 네 글자가 적혀 오는 것을 그대로 옮겼다 → 그 오류는 종류만 남긴다.
16. `seal --min-lead-hours 0`으로 마감 뒤에도 손으로 봉인할 수 있었다 → 12시간보다 늦출 수 없게 막았다.

예약 작업 "엔진 봉인"을 만들며 검토에서 고친 것(10/9 밤) — 코드를 보지 않은 검토를 한 번 돌렸다
17. 한 번 부르는 시간(360초)을 넘겨 끊긴 호출은 오류라서 세지 않았고, 20분마다 다시 불렸다. 가짜 API로 돌려 보니 한 발표에서 한 엔진을 280번 불렀다 → 오래 기다린 실패에 상한(§7-1 "답 한 번").
18. 봉인 마감 뒤에는 엔진별 상태가 비어 있어, 한 엔진만 봉인된 발표도 조종판에 "봉인됨"으로 적혔다 → 마감 뒤에도 엔진별로 봉인됨·미제출을 알려 준다.
19. 남은 시간이 한 번 부르는 시간보다 짧은 바퀴에서는 부르지도 못하면서 실패로 적혔다 → 그 바퀴는 미룬다. 앞 작업이 길어져 봇 집행 시간 안으로 들어간 경우에도 부르던 것을 막았다.
20. 두 발표가 겹치면 늘 같은 발표가 먼저 시간을 다 써서 다른 발표가 한 번도 불리지 않았다 → 바퀴마다 차례를 바꾼다.
21. 일정표의 같은 발표가 두 줄이고 앞줄의 시각을 읽을 수 없으면, 예정은 뒷줄로 잡히는데 실행기는 앞줄을 읽어 멈췄다 → 실행기도 읽을 수 없는 줄을 건너뛴다.
22. 처음 올린 코드(8120948)는 서버의 자체 시험에서 떨어져 서버가 되돌렸다(10/9 21:00). 시험이 레시피 폴더의 기본 자리를 읽었는데, 서버에는 그 자리에 진짜 레시피(한 번에 360초)가 있어 결과가 달라졌다 → 시험이 쓰는 자리를 모두 임시 폴더로 줬다. 올리기 전에 서버와 같은 상태(레시피·장부·등록·`.env`를 가짜 값으로)를 만들어 놓고 네 시험을 돌려, 그 상태에 기대지도 그 상태를 바꾸지도 않는 것을 확인했다.
