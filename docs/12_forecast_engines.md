상태: 채택(D18), 이름·실행 방식 확정(D19). **연말까지는 발표가 끝난 뒤의 성적만 공개하고, 발표 전 예측값은 어디에도 싣지 않는다(D20).** v0.3: 대상을 앞으로의 지표 경로(전망판)까지 넓히고 양쪽이 열린 해석을 싣기로 함(D21, §2-2). 콘텐츠로 내는 형태(풀이·가늠·전망판)와 티어·채널은 docs/14. v0.2: 이름 아들러/플레처와 API 자동 호출 확정, Nick의 가설 등록(§1), 시장 예상치 내부 기록(§6), 입력 자료 구조는 docs/13. 봉인·채점 코드는 `pipeline/forecast/`, 표는 `pipeline/db/schema.sql` §11, 일정표는 `data/forecast/schedule_2026Q4.csv`.
이 문서는 조사 기반 정리이며 법률 자문이 아니다.

## 0. 한 문장

**같은 자료를 두 엔진에 주고, 미국 경제지표의 발표값을 발표 전에 봉인하고, 발표 뒤 같은 자로 채점한다.**
해자는 "잘 맞힌다"가 아니라 "한 번도 빼지 않고 봉인하고 채점한 기록의 길이"다.

## 1. 왜 하는가, 무엇을 기대하는가

- **전망 체크의 짝.** 남의 전망을 채점하는 곳이 자기 전망도 같은 자로 채점한다. 장부·채점표(D12)와 같은 원리를 하나 더 쌓는 일이다.
- **일정 체크의 재미.** "수요일 밤 물가 발표"에 "두 엔진은 얼마로 봤나"가 붙는다. 구색이 풍부해진다(D14).
- **정확도는 가설로 등록하고 기록으로 가린다.**
  - Nick의 가설(10/5 등록): "최신 모델로 만든 엔진은 시장 예상치만큼 맞힌다. 아직 아니라면 곧 그렇게 된다." 사람들의 그 기대감 자체가 소구점이다.
  - 지금까지의 근거: 지표 예측을 실시간으로 잰 연구(arXiv 2608.30110)에서는 LLM이 시장 예상치와 비슷하거나 조금 못했고 물가에서 뒤졌다. 다만 평가된 것은 한 세대 전 모델이다. 일반 예측 질문에서는 최상위 LLM과 슈퍼예측가의 격차가 "LLM 발전 1년치"까지 좁혀졌고, 추세선상의 동률 시점은 2026년 11월 전후(95% 구간 2026-01 ~ 2027-11)로 추정됐다(ForecastBench, 2026-01). 최신 모델(Astra, Fable 세대)로 지표 예측을 잰 공개 결과는 찾지 못했다. → 가설이 맞는지 틀리는지 아직 아무도 재지 않았고, 우리 장부가 재는 쪽이 된다.
  - 모델과 무관하게 남는 불리함: 엔진은 시장 예상치를 입력으로 받지 못하고(유료 자료) 발표 12시간 전에 마감한다. 그래서 승부처는 입력 자료다(docs/13).
  - 가리는 방법: 핵심 발표마다 시장 예상치를 발표 전에 내부 기록으로 남기고(§6) 같은 자로 채점한다. 판정 시점은 발표 30회.
  - 기대감을 쓰는 방식: "두 AI 엔진이 맞히는지 같이 지켜본다"는 쓸 수 있다. "AI가 기관보다 정확하다"는 기록이 생기기 전에는 쓰지 않는다(단정적 판단 금지, D12).
- **정확도를 올릴 수 있는 곳은 레시피다.** 어떤 자료를 어떤 순서로 주는지, 지표를 어떻게 쪼개 묻는지, 몇 번 돌려 어떻게 합치는지. 이 부분이 비공개 로직이 된다. 내용은 감추되, 바뀌지 않았다는 것은 해시로 증명한다(§4).
- **정확도를 카피로 쓰지 않는다.** "적중률 N%"는 수익률 자랑과 같은 함정이다(D12). 틀린 것도 같은 크기로 싣는다.

## 2. 지킬 선 (D18)

1. 대상은 **연방 통계기관이 정해진 날 숫자로 발표하는 지표**뿐이다. 주가·지수·환율·개별 종목 실적·기준금리 결정은 예측하지 않는다.
2. **과거 데이터로 성능을 재지 않는다.** 모델은 과거 값을 이미 알고 있어 백테스트가 부풀려진다. 성적은 봉인 이후의 기록만 센다.
3. **엔진 = 이름 + 버전 + 기반 모델 + 레시피.** 무엇이든 바꾸려면 새 버전을 장부에 먼저 등록한다. 성적은 버전별로 따로 센다.
4. 엔진 **이름에 모델 회사·모델 이름을 넣지 않는다.**
5. 예측 문장 옆에 **가격 방향·행동 권유 문장을 두지 않는다.**
6. 엔진이 낸 값은 **사람이 고치지 않는다.** 검수는 형식과 표기만 본다.
7. **예측은 한 번만 낸다.** 같은 발표에 다시 내지 않는다.

## 2-2. 전망판과 해석 (D21)

- **전망판**: 분기 1회(FOMC 경제전망이 나오는 3·6·9·12월). 3·6·12개월 앞의 물가·실업률·성장률을 범위로 내고 연준 전망과 나란히 놓는다. 다음 발표값 예측과 같은 규칙으로 봉인하고, 해당 달의 발표값으로 채점한다. 기준금리 결정·주가·지수·환율·개별 실적은 계속 대상이 아니다. 1호 후보는 12/9 FOMC 뒤. 대상 지표와 봉인 형식은 12월 전에 정해 코드에 넣는다.
- **해석**: 숫자와 함께 엔진의 해석을 싣는다. 네 칸 — 가운데 길 / 위로 벗어나는 경우 / 아래로 벗어나는 경우 / 무엇을 보면 알 수 있나.
  1. "아들러의 해석", "플레처의 해석"으로 표시를 단다.
  2. 한쪽으로 단정하지 않는다. 양쪽 경우를 함께 쓴다.
  3. 봉인된 범위에 묶는다(위쪽 경우 = 범위의 위 끝 쪽). 다음 호에서 어느 경우였는지 되짚는다. 되짚을 수 없는 말은 쓰지 않는다.
  4. 지표와 경기에 대해서만 쓴다. 가격·종목·행동으로 잇지 않는다. 원인 단정을 쓰지 않는다.
  5. 숫자는 사실 묶음과 봉인된 범위에 있는 것만 쓴다(D17). 해석 문장은 엔진이 쓴 그대로 싣고, 규칙을 어긴 문장은 고치지 않고 뺀다.
- **종목에는 엔진을 쓰지 않는다.** 엔진은 봉인·채점되는 것만 말한다.

## 4. 엔진의 정의와 이름

**엔진 = 이름 + 버전 + 기반 모델 + 레시피 폴더 + 실행 횟수.** 레시피 폴더(`data/private/engines/<이름>/v<버전>/`)에는 프롬프트와 설정이 들어가며 밖에 내지 않는다. 등록하면 폴더 전체의 해시가 공개 장부에 남는다. 등록 뒤 파일을 하나라도 고치면 봉인 단계에서 걸린다.

레시피를 고치는 규칙: 새 버전은 먼저 '도전자'로 등록해 같은 발표를 함께 봉인하고(공개 성적에는 넣지 않음), 분기 심판 때 현 버전과 나란히 놓고 교체 여부를 정한다. 한두 번의 결과를 보고 고치지 않는다.

### 이름 — 아들러 / 플레처로 확정 (D19)

- **아들러**(`adler`) = Claude 계열 모델, **플레처**(`fletcher`) = GPT-6 Astra(`gpt-6-astra`). 짝은 엔진을 등록하기 전까지 바꿀 수 있다.
- 아래는 검토했던 후보.

| 안 | 이름 | 뜻 | 장점 | 걸리는 점 |
|---|---|---|---|---|
| **A (추천)** | **아들러 / 플레처** | 체크섬을 계산하는 실제 방법의 이름(Adler-32, Fletcher) | 브랜드와 한 줄로 이어진다. 사람 이름처럼 불려 "이번에는 아들러가 더 가까웠다"가 자연스럽다. 정확도를 약속하지 않는 이름 | 유래를 한 번은 설명해야 한다(운영자 노트 소재) |
| B | 가늠 / 어림 | 순우리말 | 쉽고 겸손하다. '예측'보다 '가늠'이라는 태도가 드러난다 | 둘의 구분이 약하다. '어림'은 허술하게 들릴 수 있다 |
| C | 눈금 / 저울 | 재는 도구 | '체크'와 어울린다 | 캐릭터가 약하고 도구 메뉴 이름과 헷갈릴 수 있다 |

- 코드에서 쓰는 이름은 영문 소문자(`adler`, `fletcher`), 화면 이름은 한글.
- 어느 엔진이 어느 모델 위에서 도는지는 **이름에는 넣지 않되, 방법 페이지의 버전 표에는 사실로 적는다.** 감추면 "과정을 공개한다"는 포지션과 어긋난다.
- 공개 전에 할 일: 상표 검색(KIPRIS), 모델 제공사의 표기 지침 확인.

## 5. 입력 — 두 엔진이 같은 사실 묶음을 본다

- 대상 지표의 과거 값(최근 36개월)과 구성 항목, 직전 발표의 수정 이력
- 발표 전에 먼저 나오는 공공 자료: 주간 휘발유 소매가(에너지정보청), 주간 실업수당 청구(노동부), 같은 달의 다른 발표(예: CPI 예측에 고용보고서)
- 달력 정보: 조사 주간, 영업일 수, 작년 같은 달의 전월비(기저 효과)
- **넣지 않는 것**: 시장 예상치(권리 없음), 기사·헤드라인(D17 원칙 — 엔진도 사실 표만 본다), 웹 검색(끈다. 켜면 남의 예상치를 옮겨 적는 복사기가 된다)
- 묶음은 파일로 저장하고 해시를 봉인 기록에 넣는다. 두 엔진에 같은 파일이 갔다는 것이 남는다.

## 6. 출력, 봉인, 채점

**출력**: 지표마다 가운데 값(p50)과 80% 구간(p10~p90). 한 점이 아니라 범위로 낸다. 발표 자릿수보다 한 자리까지만 더 잘게 쓴다.

**봉인**: 발표 한 번이 장부 기록 한 건. 마감은 **발표 12시간 전**. 공개 장부에는 발표 종류·기준 기간·엔진 목록·해시만 남고, 값은 발표 뒤에 원문으로 공개한다. 기준선("직전 발표값 그대로")도 같은 기록에 함께 봉인한다.

**코드가 막는 것**: 마감을 넘긴 봉인 / 등록되지 않은 엔진·버전 / 등록 뒤 레시피가 바뀐 엔진 / 같은 발표의 두 번째 봉인 / 기준선이 빠진 지표 / 구간 순서가 틀린 값.

**채점** (발표 다음 날):

| 보는 것 | 뜻 |
|---|---|
| 오차 | 가운데 값과 발표값의 차이 |
| 구간 적중 | 발표값이 p10~p90 안에 들어왔는가. 길게 보면 80%여야 한다. 그보다 높으면 구간이 너무 넓고, 낮으면 과신이다 |
| 구간 점수 | 구간 폭 + 벗어난 거리 × 10. 좁으면서 맞을수록 작다 |
| 기준선과 비교 | 같은 발표·같은 지표에서 "직전 값 그대로"보다 오차가 작았는가 |

- 단위가 다른 지표의 오차를 한 숫자로 합치지 않는다. 지표별로 따로 보여 준다.
- 발표 30회 미만은 "표본 부족"으로 표시한다. 한 발표 안의 값들(예: CPI 3개)은 서로 묶여 있어 발표 횟수로 센다.
- 시장 예상치·지역 연은 예측과의 비교는 권리 문제로 **내부에서만** 한다(§9). 공개 비교 대상은 당분간 "직전 값 그대로" 하나다. 쉬운 기준선이므로 이긴 것을 내세우지 않는다.
- **시장 예상치 내부 기록**: 핵심 발표(월 3~4회)마다 발표 전날 보도된 시장 예상치를 출처 주소와 함께 `data/private/forecast/consensus.csv`에 적고, 예측과 같은 때 봉인한다(값은 공개하지 않는다). 가설(§1)을 가리는 데 필요하다. 발표당 2분쯤의 손이 든다. 봉인 방식은 실행기와 함께 만든다.

|---|---|---|---|---|
| **A (확정, D19)** | 두 모델 모두 API로 자동 호출. 웹 검색 끔, 같은 묶음 | 아래 표 | 계정·키 준비 20~30분, 이후 0분 | 원칙대로. 재현 가능 |
| B | 구독 중인 앱(채팅 화면)에 묶음을 붙여 넣고 답을 옮겨 적음 | 0원 | 발표마다 5~10분 | 앱에는 보이지 않는 설정과 검색·기억 기능이 있어 "같은 자료"가 깨진다. 임시방편으로만 |
| C | 한 엔진만 먼저 | 절반 | A와 같음 | "두 엔진" 구도가 늦어진다 |

- **앱 구독과 API는 별개 결제다.** 앱 유료 구독에 API 사용량은 들어 있지 않다. 두 회사 모두 개발자 계정을 따로 만들고 카드를 등록해야 한다.
- **Astra는 API로 쓸 수 있다.** OpenAI 공식 모델 목록에 `gpt-6-astra`가 올라 있다(10/5 확인). 요금은 공식 요금표에서 확인하지 못했고(그 표에는 GPT-5.6 계열만 보였다) 제3자 사이트들은 100만 토큰당 입력 $10·출력 $50로 적고 있다. 계정을 만든 뒤 콘솔에서 확인한다.
- Nick 결정(10/5): Astra는 채팅 구독을 끊고 API 호출만 쓴다. 다른 작업에 채팅을 쓰고 있지 않은지만 확인하고 해지한다.

## 8. 공개 단계

| 단계 | 시기 | 하는 일 |
|---|---|---|
| 1 봉인 + 발표 뒤 성적 공개 (D20) | 10/13~연말 | 봉인하고 채점한다. 발표가 끝난 뒤의 성적만 금요일 레터의 작은 코너로 싣는다(시작은 11월 첫 금요일 제안). 발표 전 예측값은 싣지 않는다. 준비 과정은 메이킹 형식으로 보여 준다 — 보여 줄 것과 가릴 것은 D20 |

## 11. 마지막 검토에서 고친 것과 남은 불확실성

고친 것
1. 처음에는 전년비 지표를 더 넣으려 했으나, 전년비는 기저 효과로 대부분 정해져 "직전 값" 기준선이 지나치게 쉬운 상대가 된다. CPI·PCE 전년비 하나씩만 남기고 전월비를 중심에 뒀다.
2. "30건"의 단위를 값이 아니라 발표 횟수로 바꿨다. 한 발표 안의 값들은 함께 움직인다.
3. 단위가 다른 지표의 오차를 하나로 합친 평균을 없앴다.
4. 엔진을 나중에 추가할 때 기준선이 다시 들어와 막히는 문제를 고쳤다(값이 같으면 허용, 다르면 거부).
5. 자체 시험이 실제 날짜에 따라 달라지지 않게 고쳤다(10/14 뒤에 돌리면 틀리게 나올 뻔했다).
6. 빈 장부에 엔진이 먼저 등록되면 기점 기록이 생기지 않는 문제를 막았다.
7. 애틀랜타 연은 약관을 확인하고 지역 연은 자료를 "공공"에서 "내부 비교용·허가 확인 전"으로 낮췄다.

남은 불확실성
- Astra의 API 요금(공식 요금표 미확인), 실제 토큰 사용량(가정의 폭이 넓다)
- 엔진 실행기는 아직 없다. 지표 수집기는 노동통계국만 있고 실제 API로는 시험 전이다(docs/13)
- 주간 청구 일정(대조 전), 지표별 계열 번호와 "처음 발표값"을 받는 방법(수집기 작성 때 공식 자료와 대조)
- 규제 해석 두 건(유사투자자문 해당 여부, AI 표시 의무)
- Nick의 Windows PC에서는 아직 돌려 보지 않았다(리눅스 Python 3.10·3.13에서 자체 시험 28건 확인). `python -m pipeline.forecast.selftest`로 확인할 수 있다
