# PC 없이 도는 운영 — 조종판과 일꾼 (v0.2, 2026-10-05)

상태: 확정(D23·D24). **10/5 밤 서버에서 실제로 가동했다** — 서버(Python 3.14) 자체 시험 통과, 실제 시트 초기화, 스레드·X에 시험 글 한 건씩 게시, 게시 일꾼 cron(5분) 등록. 코드 반영도 PC 없이 한다(§5-1). 장부·수집·엔진은 아직 서버로 옮기지 않았다(§5).
관련: 콘텐츠 구조 docs/14, 글이 만들어지는 구조 docs/11. 코드 `pipeline/console/`, `pipeline/publish/threads.py`, `pipeline/publish/x.py`.

## 0. 한 문장

**Nick은 휴대폰에서 시트를 열어 문안을 고치고 "승인"만 누른다. 나머지는 서버가 한다.**
출장이 잦아 PC에서 더블클릭하는 구조는 오래 갈 수 없다(Nick, 10/5).

## 1. 구조

```
[서버 EC2]  수집(지표·뜨는 검색어·일정) → 장부 봉인 → 엔진 → 초안 생성 → 조종판에 '초안'으로 적기
                                                                        │
[조종판: Google 시트]   Nick이 휴대폰에서 본문을 고치고 상태를 '승인'으로 ──┘
                                                                        │
[서버 EC2]  5분마다 시트 읽기 → 검사 → 스레드·X에 게시 → 링크와 시각을 시트에 다시 적기 → 기록(DB)
```

- **조종판은 화면일 뿐이다.** 사실과 기록의 원천은 서버의 DB와 장부다. 시트가 지워져도 다시 만들 수 있다.
- **사람이 승인하지 않은 글은 올라가지 않는다.** 자동으로 승인되는 경로를 만들지 않는다.
- 트렌디 체크 후보는 지금 Claude 예약 작업이 알림으로 보낸다(D22). 서버로 옮기면 후보가 시트의 "후보" 탭에 바로 적힌다.

## 2. 조종판의 탭

| 탭 | 열 | 쓰임 |
|---|---|---|
| **게시 대기열** | 번호 · 예약(KST) · 채널 · 본문 · 셀프 답글 · 상태 · 검사 · 게시 링크 · 게시 시각 · 처음 문안 · 메모 | Nick이 보는 주 화면. 본문을 고치고 상태를 바꾼다 |
| **후보** | 날짜 · 번호 · 제목 · 무슨 일 · 경제와 닿는 지점 · 가설 1~3 · 반대로 볼 점 · 더 볼 것 · 선택 | 트렌디 체크 후보. 선택하면 대기열에 초안이 생긴다(서버 이전 뒤) |
| **오늘 현황** | 항목 · 마지막 실행 · 결과 · 메모 | 수집·봉인·게시가 돌았는지. 출장 중에 한눈에 |

상태의 흐름: **초안** → (Nick) **승인** → (서버) 게시 중 → **게시됨**. 걸리면 **막힘**(이유는 "검사" 칸), 미루려면 **보류**.
- 막힌 글은 본문을 고친 뒤 다시 "승인"으로 바꾸면 다시 시도한다.
- "게시 중"으로 남아 있는 줄은 도중에 멈춘 것이다. 서버가 다시 올리지 않으니(두 번 올라가는 것 방지) 실제로 올라갔는지 보고 상태를 직접 고친다.
- "처음 문안" 칸은 고치지 않는다. 서버가 처음 문안과 올린 문안을 함께 기록해 말투 기준으로 쓴다(D17).

## 3. 게시 전 검사 (코드가 막는 것)

| 검사 | 기준 |
|---|---|
| 금지어 | `templates/banned_terms.txt` — 본문과 셀프 답글 모두 |
| 본문 안의 링크 | 링크는 셀프 답글에만 (docs/05) |
| 길이 | 스레드 500자. X는 가중 길이 280 — 한글은 한 글자가 2라서 **약 140자**, 링크는 23 |
| 예약 시각 | `2026-10-09 06:30` 형식(한국 시간). 비우면 승인 즉시 |

검사는 초안이 들어올 때 한 번, 올리기 직전에 한 번 한다. 금지어 목록에 없는 표현(가격 방향, 권유)은 코드가 잡지 못한다. 그 선은 승인하는 사람이 지킨다.

## 4. 채널

| 채널 | 방식 | 한도와 비용 | 메모 |
|---|---|---|---|
| 스레드 | 공식 Threads API. 그릇 만들기 → 게시의 두 단계, 답글은 `reply_to_id` | 무료. 500자, 하루 250건. 토큰은 60일 — 매월 갱신 명령(`python -m pipeline.publish.threads refresh`) | 본인 계정 게시는 심사 없이 된다는 것은 제3자 자료 기준. 설정하면서 확인 |
| X | X API v2 `POST /2/tweets`, OAuth 1.0a | 종량제(무료 구간 없음). 글 하나 약 $0.015, 링크 든 글 약 $0.20 — 제3자 자료, 개발자 화면에서 확인 | 링크가 든 셀프 답글은 X에 달지 않는다(요금). 한글 약 140자라 스레드 문안을 그대로 쓸 수 없다 → X용 줄을 따로 둔다 |

X용 문안: 스레드 글의 첫 두세 줄을 X 길이에 맞춘 짧은 판으로 따로 만든다. 초안을 만들 때 두 줄(스레드용, X용)이 함께 대기열에 들어간다.

## 5. 서버로 옮기는 순서

| 순서 | 옮기는 것 | 서버에서 도는 주기 | 메모 |
|---|---|---|---|
| 1 | 조종판과 게시 일꾼 | 5분마다 | §6 설정이 끝나면 |
| 2 | 장부 봉인 | 화 09:40 | **장부는 한 곳에서만 쓴다.** 10/6 첫 봉인은 PC에서 하고, 그 뒤 `data/ledger/`와 `data/private/ledger/`를 서버로 옮긴 다음 PC에서는 더 돌리지 않는다. 봇 신호 파일은 서버에 이미 있다 |
| 3 | 지표 수집, 일정 체크, 뜨는 검색어 | 발표일 밤·매일 아침·하루 3번 | PC의 DB(`data/db/`)는 옮기지 않아도 된다. 서버에서 다시 받는다 |
| 4 | 엔진 실행·봉인·채점 | 발표 전날·다음 날 | 첫 봉인(10/13)을 서버에서 하는 것이 목표 |
| 5 | 실패 알림 | 작업이 실패할 때 | 텔레그램. 시트의 "오늘 현황"과 함께 |

- 코드는 비공개 저장소에 올려 서버가 받아 쓴다. `.env`, 서비스 계정 키, `data/private/`는 저장소에 올리지 않고 서버에 직접 둔다.
- **서버는 봇이 도는 기존 EC2(우분투)를 같이 쓴다 (10/5 Nick, 여유가 많음).** 조건: ① 리눅스 계정·가상환경·`.env`를 따로 두고, 이 작업의 계정이 봇 폴더(키 파일 포함)를 읽지 못하게 한다 ② 봇 집행 시각(화 23:31 전후)에는 무거운 작업을 예약하지 않는다 ③ 밖에서 들어오는 접속을 받는 것(웹사이트, 종목 체크 페이지)은 이 서버에 두지 않는다 — 그때 서버를 나눈다 ④ 디스크가 차지 않게 원문·로그 보관 기간을 둔다. 봇의 신호 파일은 읽기 전용으로만 넘겨받는다
- 봇과 리눅스 계정·가상환경·키를 나눈다(docs/11 §6). 이 작업의 계정은 봇의 키 파일을 읽지 못하게 한다.
- `data/private/`(장부 원문, 레시피, 사실 묶음)는 매일 다른 곳으로 백업한다.

## 5-1. 코드가 서버에 가는 길 (D24)

```
[Claude 세션]  저장소를 받아 고친다 → 자체 시험 → 올린다(main)
                                              │
[깃허브 비공개 저장소 romans0839-cpu/checksum]  ← 원본
                                              │  10분마다
[서버]  scripts/server_sync.sh : 받기 → 자체 시험 4종 → 통과하면 쓰고, 실패하면 직전 커밋으로 되돌림
                                              │
[조종판 "오늘 현황"]  "코드 반영" 줄에 결과 (반영 a1b2c3d → e4f5a6b / 실패: … → 되돌림)
```

- 서버는 저장소를 읽기만 한다. 서버에서 추적 중인 파일을 직접 고치면 받기가 멈추고 "받지 못함"이 현황에 뜬다.
- 반영하는 동안에는 게시 일꾼과 같은 잠금 파일을 잡아, 코드가 바뀌는 중간에 글이 올라가지 않게 한다.
- 시험에 떨어져 되돌린 커밋은 새 커밋이 올 때까지 다시 시도하지 않는다.
- PC 폴더는 사본이다. PC를 쓸 때 `sync.bat`을 더블클릭해 맞춘다.
- 서버의 지금 구성: 계정 `checksum`(봇 폴더를 읽지 못함), 코드 `~/checksum`, 봇 저장소 사본 `~/bot_readonly`(읽기 전용 키), 가상환경 `~/venv`, 키 `~/checksum/.env`·`~/keys/sa.json`(권한 600), 로그 `~/logs/`.
- 서버 cron (`checksum` 계정):

```
*/5 * * * *  cd /home/checksum/checksum && flock -n /home/checksum/logs/worker.lock /home/checksum/venv/bin/python -m pipeline.console.worker run >> /home/checksum/logs/worker.log 2>&1
*/10 * * * * bash /home/checksum/checksum/scripts/server_sync.sh >> /home/checksum/logs/sync.log 2>&1
```

## 6. Nick이 한 번 해 줄 설정 (합쳐서 1시간쯤, 나눠서 해도 된다)

화면이 아래 설명과 다르면 캡처를 보내면 된다. 키와 토큰 값은 채팅에 붙여 넣지 않는다.

**가. 시트와 서비스 계정**
1. hello@checksumlab.com의 드라이브에서 새 스프레드시트를 만들고 이름을 "체크섬 조종판"으로 한다. 주소의 `/d/`와 `/edit` 사이 문자열이 시트 ID다.
2. console.cloud.google.com에서 새 프로젝트를 만들고, "API 및 서비스 → 라이브러리"에서 Google Sheets API와 Google Drive API를 사용 설정한다.
3. "IAM 및 관리자 → 서비스 계정"에서 계정을 만들고, 그 계정의 "키" 탭에서 JSON 키를 내려받는다.
4. 시트의 "공유"에 서비스 계정 이메일(`…iam.gserviceaccount.com`)을 편집자로 넣는다.
5. 3번에서 조직 정책 때문에 키를 만들 수 없다고 나오면, 개인 Gmail 계정의 구글 클라우드에서 2~3번을 하고 4번에 그 이메일을 넣는다.

**나. 스레드**: developers.facebook.com에서 앱을 만들고 사용 사례로 Threads API를 고른다 → 권한 `threads_basic`, `threads_content_publish` → 앱 역할의 Threads 테스터에 @checksumlab을 넣고 스레드 앱 설정에서 초대를 수락한다 → 사용자 토큰을 만들고 긴 토큰(60일)으로 바꾼다. (계정 개설이 먼저다)

**다. X**: developer.x.com에서 앱을 만든다 → 사용자 인증 설정을 "읽기와 쓰기"로 → Keys and tokens에서 API Key·Secret과 Access Token·Secret을 만든다 → 소액 충전.

**라. 서버**: 이 작업용 리눅스 계정과 가상환경을 만들고 `pip install -r requirements-server.txt`. `.env`에 아래 값을 넣는다.

```
GOOGLE_SERVICE_ACCOUNT_FILE=   (JSON 키 파일 경로)
CONSOLE_SHEET_ID=
THREADS_USER_ID=
THREADS_ACCESS_TOKEN=
X_API_KEY=
X_API_SECRET=
X_ACCESS_TOKEN=
X_ACCESS_SECRET=
```

그다음 `python -m pipeline.console.worker init`(탭 만들기) → 시험 글 한 줄을 넣고 승인 → `python -m pipeline.console.worker run --dry-run`으로 확인 → `run`.

## 7. 명령

```
python -m pipeline.console.selftest                 인터넷·시트·계정 없이 구조 점검
python -m pipeline.console.worker init              조종판의 탭과 머리글 만들기
python -m pipeline.console.worker run --dry-run     올리지 않고 무엇을 할지 보기 (시트도 바꾸지 않는다)
python -m pipeline.console.worker run               한 바퀴 (서버 cron 5분마다)
python -m pipeline.console.worker add --channel 스레드 --at "2026-10-09 06:30" --text "..." --reply "..."
python -m pipeline.publish.threads refresh          스레드 토큰 갱신 (월 1회)
python -m pipeline.console.worker note --item "..." --result "..."   오늘 현황에 한 줄 (서버 작업이 결과를 남길 때)
bash scripts/server_sync.sh                         새 코드 받기 → 자체 시험 → 반영 또는 되돌림 (서버 cron 10분마다)
```

## 8. 마지막 검토에서 고친 것과 남은 불확실성

고친 것
1. 미리 보기(`--dry-run`)가 시트의 상태를 "막힘"으로 바꾸고 있었다. 미리 보기는 아무것도 쓰지 않게 고쳤다.
2. 도중에 멈춘 글이 다음 바퀴에 다시 올라갈 수 있었다. 올리기 직전에 "게시 중"으로 바꾸고, 그 상태로 남은 줄은 사람이 확인하게 했다.
3. X의 길이를 글자 수로 세고 있었다. 한글은 한 글자가 2로 계산되므로 가중 길이로 바꿨다(한글 약 140자).
4. 시트에 쓰는 값이 수식으로 해석되지 않게 했다.
5. 오류 문구와 기록에 토큰이 섞이지 않는지 시험에 넣었다.

10/5 밤 실제 가동에서 확인한 것
- 실제 시트·스레드·X에서 동작한다. 스레드는 본인 계정 게시가 심사 없이 됐고, X는 키 4개로 글이 올라갔다
- 걸린 곳: 서비스 계정의 구글 클라우드 프로젝트에서 Google Sheets API가 꺼져 있었다 → 켠 뒤 통과. 이런 경우에 긴 오류 대신 원인 한 줄이 나오게 고쳤다

남은 불확실성
- 스레드 토큰이 60일짜리인지(짧은 토큰이면 한두 시간 뒤 만료 — 만료되면 대기열에 "막힘"으로 뜬다). X의 실제 요금은 청구서로 확인
- `server_sync.sh`는 임시 저장소로만 시험했다. 서버에서의 첫 실행은 Nick이 cron을 등록한 뒤
- 자체 시험이 잡지 못하는 오류는 서버에 반영될 수 있다. 세션이 서버의 로그를 직접 볼 수 없어, 작업 결과를 "오늘 현황"에 남기는 범위를 넓혀야 한다
- 예약 작업이 만든 후보를 시트에 바로 적는 길: 지금 연결된 드라이브 도구는 시트의 칸을 고칠 수 없다(파일 만들기만 된다). 서버 이전 전까지는 고른 문안을 Nick이 대기열에 붙여 넣는다
- 인스타, 텔레그램 알림은 아직 없다
