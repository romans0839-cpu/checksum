# PC 없이 도는 운영 — 조종판과 일꾼 (v0.3, 2026-10-06)

상태: 확정(D23·D24). **10/5 밤 서버에서 실제로 가동했다** — 서버(Python 3.14) 자체 시험 통과, 실제 시트 초기화, 스레드·X에 시험 글 한 건씩 게시, 게시 일꾼 cron(5분) 등록. 코드 반영도 PC 없이 한다(§5-1). **v0.3(10/6): 지표 수집을 서버로 옮기는 코드(§5-2)와, 저장소에 올린 SNS 초안을 대기열에 '초안'으로 싣는 길(§5-3)을 올렸다.** 서버에서의 첫 실행은 Nick이 `scripts/server_cron.sh`를 한 번 돌린 뒤다. 장부·엔진·일정 체크·뜨는 검색어는 아직 서버로 옮기지 않았다(§5).
관련: 콘텐츠 구조 docs/14, 글이 만들어지는 구조 docs/11. 코드 `pipeline/console/`, `pipeline/publish/threads.py`, `pipeline/publish/x.py`.

## 0. 한 문장

**Nick은 휴대폰에서 시트를 열어 문안을 고치고 "승인"만 누른다. 나머지는 서버가 한다.**
출장이 잦아 PC에서 더블클릭하는 구조는 오래 갈 수 없다(Nick, 10/5).

## 1. 구조

```
[서버 EC2]  수집(지표·뜨는 검색어·일정) → 장부 봉인 → 엔진 → 초안 생성 → 조종판에 '초안'으로 적기
                                                                        │
[조종판: Google 시트]   Nick이 휴대폰에서 본문을 고치고 상태를 '승인'으로 ──┘
                                                                        │
[서버 EC2]  5분마다 시트 읽기 → 검사 → 스레드·X에 게시 → 링크와 시각을 시트에 다시 적기 → 기록(DB)
```

- **조종판은 화면일 뿐이다.** 사실과 기록의 원천은 서버의 DB와 장부다. 시트가 지워져도 다시 만들 수 있다.
- **사람이 승인하지 않은 글은 올라가지 않는다.** 자동으로 승인되는 경로를 만들지 않는다.
- 트렌디 체크 후보는 지금 Claude 예약 작업이 알림으로 보낸다(D22). 서버로 옮기면 후보가 시트의 "후보" 탭에 바로 적힌다.

## 2. 조종판의 탭

| 탭 | 열 | 쓰임 |
|---|---|---|
| **게시 대기열** | 번호 · 예약(KST) · 채널 · 본문 · 셀프 답글 · 상태 · 검사 · 게시 링크 · 게시 시각 · 처음 문안 · 메모 | Nick이 보는 주 화면. 본문을 고치고 상태를 바꾼다 |
| **후보** | 날짜 · 번호 · 제목 · 무슨 일 · 경제와 닿는 지점 · 가설 1~3 · 반대로 볼 점 · 더 볼 것 · 선택 | 트렌디 체크 후보. 선택하면 대기열에 초안이 생긴다(서버 이전 뒤) |
| **오늘 현황** | 항목 · 마지막 실행 · 결과 · 메모 | 수집·봉인·게시가 돌았는지. 출장 중에 한눈에 |

상태의 흐름: **초안** → (Nick) **승인** → (서버) 게시 중 → **게시됨**. 걸리면 **막힘**(이유는 "검사" 칸), 미루려면 **보류**.
- 막힌 글은 본문을 고친 뒤 다시 "승인"으로 바꾸면 다시 시도한다.
- "게시 중"으로 남아 있는 줄은 도중에 멈춘 것이다. 서버가 다시 올리지 않으니(두 번 올라가는 것 방지) 실제로 올라갔는지 보고 상태를 직접 고친다.
- "처음 문안" 칸은 고치지 않는다. 서버가 처음 문안과 올린 문안을 함께 기록해 말투 기준으로 쓴다(D17).

| 검사 | 기준 |

| 본문 안의 링크 | 링크는 셀프 답글에만 (docs/05) |

| 순서 | 옮기는 것 | 서버에서 도는 주기 | 메모 |

| 4 | 엔진 실행·봉인·채점 | 발표 전날·다음 날 | 첫 봉인(10/13)을 서버에서 하는 것이 목표 |

- `data/private/`(장부 원문, 레시피, 사실 묶음)는 매일 다른 곳으로 백업한다.

## 5-1. 코드가 서버에 가는 길 (D24)

```
[Claude 세션]  저장소를 받아 고친다 → 자체 시험 → 올린다(main)
                                              │
[깃허브 비공개 저장소 romans0839-cpu/checksum]  ← 원본
                                              │  10분마다
[서버]  scripts/server_sync.sh : 받기 → 자체 시험 4종 → 통과하면 쓰고, 실패하면 직전 커밋으로 되돌림
                                              │
[조종판 "오늘 현황"]  "코드 반영" 줄에 결과 (반영 a1b2c3d → e4f5a6b / 실패: … → 되돌림)
```

- 서버는 저장소를 읽기만 한다. 서버에서 추적 중인 파일을 직접 고치면 받기가 멈추고 "받지 못함"이 현황에 뜬다.
- 반영하는 동안에는 게시 일꾼과 같은 잠금 파일을 잡아, 코드가 바뀌는 중간에 글이 올라가지 않게 한다.
- 시험에 떨어져 되돌린 커밋은 새 커밋이 올 때까지 다시 시도하지 않는다.
- PC 폴더는 사본이다. PC를 쓸 때 `sync.bat`을 더블클릭해 맞춘다.
- 서버의 지금 구성: 계정 `checksum`(봇 폴더를 읽지 못함), 코드 `~/checksum`, 봇 저장소 사본 `~/bot_readonly`(읽기 전용 키), 가상환경 `~/venv`, 키 `~/checksum/.env`·`~/keys/sa.json`(권한 600), 로그 `~/logs/`.
- 서버 cron (`checksum` 계정)은 세 줄이다. 손으로 넣지 않고 **`cd ~/checksum && git pull && bash scripts/server_cron.sh`** 한 번으로 맞춘다(여러 번 돌려도 같다. 이미 손으로 넣은 같은 줄은 기준 줄로 바뀌고 다른 줄은 그대로 둔다). 넣는 줄은 `bash scripts/server_cron.sh --show`로 미리 볼 수 있다:

```
*/5 * * * *    cd ~/checksum && flock -n ~/logs/worker.lock timeout 600 ~/venv/bin/python -m pipeline.console.worker run >> ~/logs/worker.log 2>&1     게시 일꾼
*/10 * * * *   bash ~/checksum/scripts/server_sync.sh >> ~/logs/sync.log 2>&1                                                                          코드 반영
2-59/5 * * * * cd ~/checksum && flock -w 100 ~/logs/worker.lock timeout 600 ~/venv/bin/python -m pipeline.console.jobs tick >> ~/logs/jobs.log 2>&1    예약 작업 일꾼
```

- 세 줄은 같은 잠금 파일을 쓴다. 코드가 바뀌는 중간에 글이 올라가거나 수집이 돌지 않는다. 예약 작업 일꾼은 게시 일꾼과 겹치지 않게 2분 어긋나 있다.
- 일꾼 두 줄에는 `timeout 600`을 건다. 바깥 서비스(시트, SNS)가 응답하지 않아 멈춰 있으면 잠금을 쥔 채라 게시·수집·코드 반영이 모두 서기 때문이다. 게시 도중에 끊긴 줄은 "게시 중"으로 남고, 그 줄은 사람이 확인한다(§2). 시트 호출 자체에도 제한 시간(연결 10초, 응답 60초)을 뒀다.

## 5-2. 예약 작업 일꾼 — 수집·봉인 같은 서버 작업이 도는 길 (10/6)

```
[서버 cron, 5분마다]  python -m pipeline.console.jobs tick
        │  예정은 cron 이 아니라 저장소의 작업표(pipeline/console/jobs.py)와 발표 일정표(data/forecast/schedule_*.csv)가 정한다
        ▼
때가 된 작업을 한 번 실행 → DB(job_run)에 기록 → 조종판 "오늘 현황"에 작업마다 한 줄
```

- **작업을 더하거나 시각을 바꿀 때 서버에 들어갈 필요가 없다.** 저장소에 올리면 10분 안에 반영된다(D24). cron 은 `tick`만 부른다.
- 예정 하나는 끝날 때까지 정해진 간격으로 다시 시도하고, 유효 시간이 지나면 그만둔다. 한 작업이 실패하거나 조종판을 열지 못해도 다른 작업과 게시 일꾼은 그대로 돈다.
- 화요일 23:20~23:50(한국 시간)에는 돌리지 않는다. 같은 서버에서 봇이 주문을 내는 시간이다(§5의 조건 ②). 봇 집행 시각이 바뀌면 `jobs.py`의 `QUIET`을 고친다.
- 세션은 서버의 로그를 볼 수 없다. 그래서 고칠 때 필요한 내용(제목이 맞지 않는 계열과 API가 돌려준 제목, 오지 않은 계열, 다음 예정)을 "오늘 현황"의 메모 칸에 그대로 적는다. 키 값은 화면·기록·원문 어디에도 남기지 않는다.

지금 있는 작업

| 항목(오늘 현황) | 언제 | 하는 일 | 실패하면 |
|---|---|---|---|
| 지표 수집 | 매일 07:10 + 노동통계국 발표(CPI·고용·PPI) 2분 뒤 | 노동통계국 계열 27개를 받아 DB에 쌓고, 발표가 지난 대상의 처음 발표값을 `data/forecast/actuals.csv`에 적는다 (docs/13) | 아침 수집은 60분마다 다시(하루 안), 발표 직후는 발표값이 올 때까지 10분마다(3시간 안) |
| 초안 싣기 | 저장소에 새 초안 파일이 올라오면(5분 안) | `data/sns/drafts/*.md`의 초안을 게시 대기열에 '초안'으로 싣는다 (§5-3) | 30분마다 다시, 네 번까지 |
| 고친 기록 | 매시 7분 | 승인·게시된 줄에서 Nick이 고친 문장을 모아 "고친 기록" 탭에 적는다 (§5-4). 새로 고친 것이 없으면 아무것도 적지 않는다 | 그 시간 안에 한 번 더 |

- 일정표에 읽을 수 없는 줄이 있어도 일꾼은 돈다. 그 줄은 건너뛰고 "지표 수집" 메모에 [주의]로 적는다. 한 작업이 예정을 읽다 멈춰도 다른 작업은 돈다.

"오늘 현황"의 "지표 수집" 줄 읽는 법
- `정상 · 새 값 N / 수정 M / 그대로 K · 최근 달 2026-08` — 잘 돌았다. 메모에 "처음 발표값 기록: …"이 있으면 그날 발표값이 들어온 것이다
- `주의 n건 · …` — 돌았지만 볼 것이 있다. 메모의 [주의] 줄을 그대로 Claude에게 알려 주면 된다(계열 번호를 고친다)
- `실패: …` — 이유가 적혀 있다. "BLS_API_KEY 가 없음"이면 서버 `.env`에 그 줄을 넣는다. 접속 실패는 알아서 다시 시도한다

## 5-3. 초안이 조종판에 들어오는 길 — 저장소의 초안 파일 (10/6)

```
[Claude 세션·예약 작업]  초안 파일을 저장소에 올린다  data/sns/drafts/<날짜>_<이름>.md
                                   │  서버가 코드와 함께 받는다(10분 안)
[서버 예약 작업 일꾼 "초안 싣기"]  아직 싣지 않은 초안을 게시 대기열 끝에 적는다 — 상태는 언제나 '초안'
                                   │
[Nick, 휴대폰]  본문을 고치고 상태를 '승인'으로 → 게시 일꾼이 예약 시각에 올린다
```

- **싣는 상태는 '초안'뿐이다.** 승인은 사람만 한다. 이 길로 들어온 글도 승인하지 않으면 올라가지 않는다.
- 초안 하나가 채널마다 한 줄이 된다(스레드 한 줄, X 한 줄). 메모 칸에 초안 이름·줄기·조건이 적힌다. **조건이 적힌 줄은 그 조건이 맞을 때만 승인한다.**
- 나중에 채워야 하는 값은 `[채울 것: 무엇]`으로 적혀 있다. 채우지 않고 승인하면 게시 일꾼이 "막힘"으로 돌리고 이유를 적는다(괄호 한쪽이 지워져도 잡는다). 다 채웠으면 그 표시를 통째로 지운다.
- 한 번 실은 초안은 다시 싣지 않는다. 실은 뒤에는 시트가 기준이다. 저장소의 파일을 고쳐도 시트의 줄은 바뀌지 않는다(다시 실으려면 초안 이름 끝에 `-v2`). 실었다는 기록을 잃어도 시트에 같은 줄이 있으면 두 번 넣지 않는다.
- 예약 시각이 비어 있는 초안(예비 글)은 승인하는 즉시 올라간다.
- 형식이 틀린 초안 파일은 통째로 싣지 않고 "오늘 현황"의 "초안 싣기" 줄에 이유를 적는다.
- 올리기 전에 세션이 돌리는 검사: `python -m pipeline.console.drafts check data/sns/drafts/<파일>.md` (길이·금지어·본문 링크·형식). 금지어 목록에 없는 표현(가격 방향, 권유)은 이 검사가 잡지 못한다. 그 선은 쓰는 쪽과 승인하는 사람이 지킨다.
- 파일 형식은 `pipeline/console/drafts.py` 머리말에 있다. 지금 파일: `data/sns/drafts/2026-10-09_two_weeks_v2.md`(스레드 첫 2주치, D27 방향으로 다시 쓴 판. 첫 판 `…first_two_weeks.md`는 10/6 전부 기각되어 저장소에서 지웠다 — 시트에 이미 실린 46줄은 Nick이 지운다).
- `drafts check`는 `templates/avoid_terms.txt`의 말(예: 봉인)이 본문이나 답글에 있으면 걸러 낸다(D27). 서버는 이것으로 글을 막지 않는다.

## 5-4. 고친 문장이 다음 초안으로 돌아가는 길 — "고친 기록" 탭 (10/6)

```
[Nick, 휴대폰]  초안의 문장을 고치고 '승인'
        │
[서버 "고친 기록" 작업, 매시 7분]  승인·게시된 줄의 '처음 문안'과 '본문'을 문장 단위로 견줘, 달라진 곳만 DB(sns_edit)와 "고친 기록" 탭에 적는다
        │
[Claude 세션·예약 작업]  초안을 쓰기 전에 드라이브 도구로 "체크섬 조종판"의 "고친 기록" 탭을 읽는다 → 말투 지침(templates/voice_guide.md)에 반영
```

- 조종판 시트는 Claude에 연결된 구글 계정에 **보기 전용**으로 공유되어 있다(10/6 Nick). 세션은 읽기만 한다. 시트에 쓰는 것은 서버뿐이다.
- 종류는 넷이다: 바꿈 / 지움 / 더함 / 채움(`[채울 것: …]`을 채운 것 — 운영자 노트처럼 Nick이 직접 쓴 문장이라 말투 표본으로 가장 좋다).
- 고치는 중인 초안과 보류한 줄은 보지 않는다. 승인한 뒤의 문장만 "Nick이 고른 말"로 친다.
- 탭은 최근 것부터 80줄, 한 칸은 220자까지다. 세션이 드라이브 도구로 시트를 읽으면 긴 칸(250자쯤)과 뒤쪽 줄(26줄쯤 뒤)이 잘려서 온다. 그래서 게시 대기열을 직접 견주지 않고 이 탭을 본다. 전체 기록은 서버 DB에 있다.
- 이 탭은 서버가 통째로 다시 쓴다. 사람이 고쳐도 다음에 지워진다. 게시 대기열과 후보 탭은 코드가 통째로 바꿀 수 없게 막아 두었다.
- 같은 공유 덕분에 세션이 "오늘 현황"도 읽을 수 있다. 코드를 올린 뒤 "코드 반영" 줄과 각 작업의 줄로 서버의 결과를 확인한다(D24의 남는 위험 ③이 줄었다).
- 말투 지침에 반영하는 때: 초안을 쓸 때마다 훑고, 금요일 주간 리뷰에서 그 주의 고침을 모아 `templates/voice_guide.md` §2를 고친다.

## 6. Nick이 한 번 해 줄 설정 (합쳐서 1시간쯤, 나눠서 해도 된다)

화면이 아래 설명과 다르면 캡처를 보내면 된다. 키와 토큰 값은 채팅에 붙여 넣지 않는다.

**가. 시트와 서비스 계정**
1. hello@checksumlab.com의 드라이브에서 새 스프레드시트를 만들고 이름을 "체크섬 조종판"으로 한다. 주소의 `/d/`와 `/edit` 사이 문자열이 시트 ID다.
2. console.cloud.google.com에서 새 프로젝트를 만들고, "API 및 서비스 → 라이브러리"에서 Google Sheets API와 Google Drive API를 사용 설정한다.
3. "IAM 및 관리자 → 서비스 계정"에서 계정을 만들고, 그 계정의 "키" 탭에서 JSON 키를 내려받는다.
4. 시트의 "공유"에 서비스 계정 이메일(`…iam.gserviceaccount.com`)을 편집자로 넣는다.
5. 3번에서 조직 정책 때문에 키를 만들 수 없다고 나오면, 개인 Gmail 계정의 구글 클라우드에서 2~3번을 하고 4번에 그 이메일을 넣는다.

**나. 스레드**: developers.facebook.com에서 앱을 만들고 사용 사례로 Threads API를 고른다 → 권한 `threads_basic`, `threads_content_publish` → 앱 역할의 Threads 테스터에 @checksumlab을 넣고 스레드 앱 설정에서 초대를 수락한다 → 사용자 토큰을 만들고 긴 토큰(60일)으로 바꾼다. (계정 개설이 먼저다)

**다. X**: developer.x.com에서 앱을 만든다 → 사용자 인증 설정을 "읽기와 쓰기"로 → Keys and tokens에서 API Key·Secret과 Access Token·Secret을 만든다 → 소액 충전.

**라. 서버**: 이 작업용 리눅스 계정과 가상환경을 만들고 `pip install -r requirements-server.txt`. `.env`에 아래 값을 넣는다.

```
GOOGLE_SERVICE_ACCOUNT_FILE=   (JSON 키 파일 경로)
CONSOLE_SHEET_ID=
THREADS_USER_ID=
THREADS_ACCESS_TOKEN=
X_API_KEY=
X_API_SECRET=
X_ACCESS_TOKEN=
X_ACCESS_SECRET=
```

그다음 `python -m pipeline.console.worker init`(탭 만들기) → 시험 글 한 줄을 넣고 승인 → `python -m pipeline.console.worker run --dry-run`으로 확인 → `run`.

## 7. 명령

```
python -m pipeline.console.selftest                 인터넷·시트·계정 없이 구조 점검

python -m pipeline.console.worker run --dry-run     올리지 않고 무엇을 할지 보기 (시트도 바꾸지 않는다)
python -m pipeline.console.worker run               한 바퀴 (서버 cron 5분마다)
python -m pipeline.console.worker add --channel 스레드 --at "2026-10-09 06:30" --text "..." --reply "..."
python -m pipeline.publish.threads refresh          스레드 토큰 갱신 (월 1회)
python -m pipeline.console.worker note --item "..." --result "..."   오늘 현황에 한 줄 (서버 작업이 결과를 남길 때)

bash scripts/server_cron.sh                         서버 예약 세 줄 맞추기 + 지표 수집 한 번 돌려 보기 (서버에서 한 번. --show 는 보기만)
python -m pipeline.console.jobs tick                때가 된 예약 작업 돌리기 (서버 cron 5분마다. --dry-run 은 보기만)
python -m pipeline.console.jobs plan                앞으로 8일의 예정 (한국 시간)
python -m pipeline.console.jobs run collect_indicators   시각과 무관하게 지금 한 번
python -m pipeline.console.drafts check data/sns/drafts/<파일>.md   초안 파일을 올리기 전 검사 (아무것도 쓰지 않는다)
python -m pipeline.console.drafts pending           아직 대기열에 싣지 않은 초안 (서버)
```

## 8. 마지막 검토에서 고친 것과 남은 불확실성

고친 것
1. 미리 보기(`--dry-run`)가 시트의 상태를 "막힘"으로 바꾸고 있었다. 미리 보기는 아무것도 쓰지 않게 고쳤다.
2. 도중에 멈춘 글이 다음 바퀴에 다시 올라갈 수 있었다. 올리기 직전에 "게시 중"으로 바꾸고, 그 상태로 남은 줄은 사람이 확인하게 했다.
3. X의 길이를 글자 수로 세고 있었다. 한글은 한 글자가 2로 계산되므로 가중 길이로 바꿨다(한글 약 140자).
4. 시트에 쓰는 값이 수식으로 해석되지 않게 했다.
5. 오류 문구와 기록에 토큰이 섞이지 않는지 시험에 넣었다.

10/5 밤 실제 가동에서 확인한 것
- 실제 시트·스레드·X에서 동작한다. 스레드는 본인 계정 게시가 심사 없이 됐고, X는 키 4개로 글이 올라갔다
- 걸린 곳: 서비스 계정의 구글 클라우드 프로젝트에서 Google Sheets API가 꺼져 있었다 → 켠 뒤 통과. 이런 경우에 긴 오류 대신 원인 한 줄이 나오게 고쳤다

10/6 지표 수집을 서버로 옮기면서 (v0.3)
- 고친 것: ① 노동통계국은 잘못된 키로 요청하면 오류 문구에 그 키를 실어 돌려줄 수 있다. 화면·"오늘 현황"·원문에 남기 전에 가리게 했다 ② 실패한 직후 사람이 다시 돌려도 간격 규칙 때문에 아무 일도 일어나지 않던 것을, 직접 돌릴 때는 간격을 따지지 않게 했다 ③ 게시 일꾼과 예약 작업 일꾼이 같은 분에 시작하면 한쪽이 매번 밀릴 수 있어 2분 어긋나게 했다 ④ PC의 `collect_indicators.bat`은 저장하지 않는 확인용으로 바꿨다(기록은 서버 한 곳에만)
- 독립 검토(코드를 쓰지 않은 쪽이 따로 재현)에서 나와 고친 것: ⑤ 일정표에 날짜가 빈 줄 하나가 있으면 수집이 도중에 멈추고 DB를 쥔 채로 남아, 5분마다 API만 부르고 아무것도 기록하지 못하던 것 → 못 읽는 줄은 건너뛰고 알리며, 쓰다 멈추면 되돌리고 닫는다 ⑥ 한 작업이 예정을 읽다 멈추면 모든 작업이 서던 것 → 작업마다 따로 감쌌다 ⑦ `[채울 것: …]` 검사가 괄호 한쪽만 지워져도 뚫리던 것 → 변형까지 잡는다 ⑧ 형식이 틀린 초안 파일이 아무 알림 없이 영영 건너뛰어지던 것 → 한 번 알린다 ⑨ 실었다는 기록을 잃으면 초안이 두 번 실리던 것 → 시트에 있는 줄은 다시 넣지 않는다 ⑩ `server_cron.sh`가 예약을 읽지 못한 것을 "예약 없음"으로 알고 다른 줄을 지울 수 있던 것, 비슷하게 생긴 남의 줄을 지우던 것 ⑪ 시트가 응답하지 않으면 잠금을 쥔 채 멈춰 게시·수집·코드 반영이 모두 서는 것 → 제한 시간
- 남은 것: **실제 노동통계국 응답으로는 아직 한 번도 돌지 않았다**(이 작업 환경에서는 접속이 막혀 있다). 서버의 첫 실행이 실제 시험이다 · 서버 `.env`에 `BLS_API_KEY`가 있는지 모른다(없으면 "실패: … 없음"으로 적힌다) · 서버에서 노동통계국 API에 닿는지 모른다 · DB와 `actuals.csv`의 백업이 아직 없다(알게 된 시각은 다시 만들 수 없으므로 첫 봉인 10/13 전에 백업 작업을 더한다) · 원문은 하루 한두 개씩 쌓인다(파일 하나 수백 KB 어림, 보관 기간은 아직 없음) · 실패 알림은 아직 시트뿐이다(텔레그램은 §5의 5번)

남은 불확실성
- 스레드 토큰이 60일짜리인지(짧은 토큰이면 한두 시간 뒤 만료 — 만료되면 대기열에 "막힘"으로 뜬다). X의 실제 요금은 청구서로 확인
- `server_sync.sh`와 `server_cron.sh`는 임시 폴더(가짜 crontab)로만 시험했다. 서버에서의 첫 실행은 Nick이 `server_cron.sh`를 돌린 뒤
- 자체 시험이 잡지 못하는 오류는 서버에 반영될 수 있다. 세션이 서버의 로그를 직접 볼 수 없어, 작업 결과를 "오늘 현황"에 남기는 범위를 넓혀야 한다
- 예약 작업이 만든 후보를 시트에 바로 적는 길: 이제 초안 파일을 저장소에 올리면 대기열에 '초안'으로 들어간다(§5-3). 예약 작업 "트렌디 체크 후보"가 고른 문안을 이 길로 올리게 바꾸는 것은 아직 하지 않았다(그 전까지는 고른 문안을 Nick이 대기열에 붙여 넣는다). "후보" 탭에 후보를 적는 길은 아직 없다
- 시트에 열을 끼워 넣으면 일꾼이 한 칸씩 밀려 쓴다(열 이름으로 읽고 열 자리로 쓴다). 열을 더하거나 옮기지 않는다
- 인스타, 텔레그램 알림은 아직 없다
